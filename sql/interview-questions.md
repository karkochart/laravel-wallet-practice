# Вопросы по SQL/PostgreSQL, которые могут задать (с короткими ответами)

Для HR-этапа достаточно знать «верхний слой» (помечено 🟢). Глубже (🔵) - для техинтервью с лидом. Отвечайте с примером из своей практики, а не определением.

## Индексы и планы
1. 🟢 **Зачем индекс и чем он вредит?** Ускоряет чтение по условию/сортировке, но замедляет INSERT/UPDATE/DELETE, занимает место, мешает HOT-обновлениям. Лишние индексы - минус.
2. 🟢 **Составной индекс `(a, b)`: когда сработает?** Для `WHERE a=?`, `WHERE a=? AND b=?`, `WHERE a=? ORDER BY b`. Для `WHERE b=?` одного - как правило нет (правило левого префикса). Равенства сначала, диапазон/сортировка последними.
3. 🟢 **Почему запрос не использует индекс?** Функция/приведение над колонкой (`WHERE date(created_at)=...`, `WHERE lower(email)=...` без выражения-индекса), несовпадение типов, `LIKE '%x'`, низкая селективность (планировщик выберет Seq Scan - и будет прав), устаревшая статистика (`ANALYZE`), мало строк в таблице.
4. 🟢 **Как читать `EXPLAIN (ANALYZE, BUFFERS)`?** Смотрим узлы снизу вверх; сравниваем `rows` оценённые и фактические (большой разрыв = плохая статистика); `Seq Scan` на большой таблице с фильтром, `Sort` на диске, `Nested Loop` с большим `loops`, `Buffers: read` (диск) против `hit` (кэш).
5. 🔵 **Типы индексов:** B-tree (дефолт, =, <, >, ORDER BY), Hash (только =), GIN (jsonb, массивы, полнотекст), GiST (геометрия, диапазоны), BRIN (огромные append-only таблицы, коррелирующие с физ. порядком - логи по времени).
6. 🔵 **Covering (`INCLUDE`), partial, expression index.** Index-only scan читает только индекс (нужна свежая visibility map, т.е. VACUUM). Partial: `... WHERE status='pending'` - маленький и быстрый. Expression: `(lower(email))`.
7. 🔵 **Виды JOIN в плане:** Nested Loop (мало строк слева + индекс справа), Hash Join (большие, без порядка), Merge Join (оба отсортированы).
8. 🔵 **`CREATE INDEX CONCURRENTLY`** - не блокирует запись, но дольше и не в транзакции. На проде крупной таблицы - только так.

## Транзакции, блокировки, конкурентность (ядро для финтеха)
9. 🟢 **ACID одной фразой каждое.** Atomicity - всё или ничего; Consistency - ограничения соблюдены; Isolation - параллельные транзакции не видят промежуточного; Durability - после COMMIT не потеряется (WAL).
10. 🟢 **Уровни изоляции в PG.** По умолчанию Read Committed (каждый запрос видит свежий снимок). Repeatable Read - один снимок на транзакцию (в PG нет фантомов, но возможен serialization failure - надо ретраить). Serializable - SSI, тоже с ретраями. Read Uncommitted в PG = Read Committed.
11. 🟢 **Как не потерять деньги при параллельном списании?** `SELECT ... FOR UPDATE` на счёт в транзакции, проверка баланса, `UPDATE balance = balance - ?`; либо условный `UPDATE ... WHERE balance >= ?` и проверка числа затронутых строк; либо оптимистичная блокировка (version) с ретраем. Плюс `CHECK (balance >= 0)` как страховка.
12. 🟢 **Что такое deadlock и как избежать?** Две транзакции ждут друг друга. Лечится единым порядком блокировок (по id), короткими транзакциями, ретраем на `40P01`. PG сам убивает одну из жертв.
13. 🔵 **`FOR UPDATE` vs `NOWAIT` vs `SKIP LOCKED` vs `FOR NO KEY UPDATE`.** NOWAIT - сразу ошибка, SKIP LOCKED - пропустить занятые (очереди задач), `NO KEY UPDATE` слабее и не блокирует FK-вставки в дочерние таблицы.
14. 🔵 **MVCC.** UPDATE создаёт новую версию строки, старая остаётся до VACUUM. Отсюда bloat, роль autovacuum и опасность долгих транзакций (держат старые версии, VACUUM не может их убрать).
15. 🟢 **Идемпотентность в БД.** Уникальный индекс по ключу операции + `INSERT ... ON CONFLICT DO NOTHING/UPDATE`. Для вебхуков: `(chain, txid, vout)`. Для API платежей: `Idempotency-Key` + хеш параметров.
16. 🔵 **Advisory locks** (`pg_advisory_xact_lock(key)`) - прикладные блокировки по произвольному ключу, когда нечего лочить строкой.
17. 🔵 **Outbox-паттерн.** Событие пишется в таблицу в той же транзакции, что и изменение; отдельный воркер публикует его в брокер. Решает «БД обновили, а сообщение не ушло».

## Модель данных для денег
18. 🟢 **Почему не float.** Двоичная дробь не хранит 0.1 точно; суммы копят ошибку. Хранить целое в минимальных единицах (satoshi, wei) либо `NUMERIC`. В PHP - строки + BCMath/GMP, а не `(float)`/`int` (wei не влезает в int64).
19. 🟢 **Баланс: поле или сумма проводок?** Источник истины - неизменяемый журнал проводок (double-entry); баланс - кэш/проекция, поддерживаемая в той же транзакции и сверяемая (reconciliation). Задание №1 в drills.
20. 🔵 **`NUMERIC(78,0)`** вмещает uint256 (до 78 десятичных цифр) - для токенов с 18 decimals.
21. 🟢 **bigint vs UUID как PK.** bigint компактнее и последователен (хорошо для B-tree); UUIDv4 случаен (фрагментация индекса, больше места), UUIDv7 упорядочен по времени - лучший компромисс, если нужен несквозной публичный id.

## Запросы
22. 🟢 **`WHERE` vs `HAVING`.** WHERE фильтрует строки до группировки, HAVING - группы после.
23. 🟢 **`UNION` vs `UNION ALL`.** UNION убирает дубли (сортировка/хеш = дорого); если дубли невозможны - ALL.
24. 🟢 **`NOT IN` и NULL.** Если в подзапросе есть NULL, `NOT IN` не вернёт ничего. Используйте `NOT EXISTS`.
25. 🟢 **Оконные функции.** `ROW_NUMBER/RANK/LAG/LEAD`, `SUM() OVER (PARTITION BY ... ORDER BY ...)` - бегущие итоги, топ-N в группе, разница с предыдущей строкой. Не схлопывают строки, в отличие от GROUP BY.
26. 🟢 **CTE.** Читаемость; с PG12 не материализуется без необходимости (можно управлять `MATERIALIZED`/`NOT MATERIALIZED`). Рекурсивные CTE - деревья/графы.
27. 🟢 **N+1 в Laravel.** Цикл по моделям с обращением к relation → N запросов. Лечится `with()` (eager loading), `withCount`, `load`. Детектить: `Model::preventLazyLoading()`, Telescope/Debugbar.
28. 🟢 **Пагинация.** `OFFSET N` читает и выбрасывает N строк - деградирует. Keyset: `WHERE id < :last ORDER BY id DESC LIMIT 20` (в Laravel - `cursorPaginate`).
29. 🟢 **`COUNT(*)` в PG медленный на больших таблицах** (нужен проход по таблице/индексу, MVCC). Решения: приблизительный счётчик из `pg_class.reltuples`, отдельный счётчик, кэш, избегать total в пагинации.
30. 🔵 **Партиционирование.** Декларативное по диапазону дат для журнальных таблиц: быстрый DROP старых партиций, partition pruning. Ограничение: уникальный ключ обязан включать ключ партиционирования.

## Эксплуатация
31. 🟢 **Что делать, если запрос внезапно стал медленным?** `EXPLAIN ANALYZE`, смотрим что изменилось (данные выросли, статистика, индекс), `pg_stat_statements` для топа по времени, `pg_stat_activity` на блокировки и долгие транзакции.
32. 🔵 **Миграции без простоя.** Добавление колонки с дефолтом в PG11+ - мгновенно; `ADD CONSTRAINT ... NOT VALID` + `VALIDATE`; индексы `CONCURRENTLY`; не держать долгих транзакций; expand/contract при переименованиях.
33. 🔵 **pgbouncer и пул.** Лимит соединений PG; transaction pooling ломает session-фичи (prepared statements, advisory session locks, `SET`).
34. 🔵 **Репликация и read-your-writes.** Реплика отстаёт - после записи читать с мастера, отчёты - с реплики.

## Стандартные Laravel-вопросы про БД
- `DB::transaction(fn, attempts)` ретраит при deadlock; вложенные транзакции = savepoint.
- `lockForUpdate()`, `sharedLock()`; `firstOrCreate` не атомарен без unique-индекса - ловите `UniqueConstraintViolationException`.
- `insertOrIgnore`, `upsert([...], uniqueBy, update)`; `chunkById` вместо `chunk` при изменении данных; `cursor()`/`lazy()` для больших выборок.
- Деньги в Eloquent: casts на `decimal:N` вернут строку; для NUMERIC(78,0) - свой cast на строку, считать bcmath.
